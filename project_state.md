## 4. Data Access (Supabase / PostgREST) Gotchas

- **Filters vs order/limit ordering:** `.eq/.ilike/.gt/.or/.not/.lt` return a `PostgrestTransformBuilder`; `.order()`/`.limit()` are on the transform builder and **return a new builder**. Correct chain: `select().filter...await builder.order().limit()`. Never put `.order()/.limit()` before filters.
- `.not()` signature is `.not(String column, String operator, Object? value)` — e.g. `.not('status', 'in', ['completed', 'cancelled'])`.
- `.count()` returns an int-like value directly (`FetchOptions`/`CountOption` are gone in postgrest 2.x).
- Gotrue: no `resendOtp` — resend is `signInWithOtp(phone: ..., channel: OtpChannel.sms)`; `verifyOTP` requires `OtpType.sms`.
- `SupabaseService` is a static singleton (`SupabaseService.instance.client`); repos call it at 13+ sites including `connectivity_provider.dart`.

## 5. Auth & Session (Supabase Auth)

- Phone-OTP sign in/sign up via Gotrue; session restored through `AuthProvider.checkSession()` on startup. NOTE: phone auth is currently **disabled** at the Supabase project level — email/password works; phone-OTP flows need it enabled in the dashboard.
- `needsOnboarding` = user has no linked business → `OnboardingPage` (create business).
- Onboarding writes `businesses` (owner_id = uid) then the owner's `business_partners` row; RLS helpers `my_business_id()` / `is_business_owner()` / `my_phone()` (all SECURITY DEFINER) make this chicken-and-egg flow work, including `INSERT … RETURNING` (which is re-checked against the SELECT policy) and invite claiming by phone.
- Logout clears the Supabase session.

**RLS pitfalls fixed in the live schema (2026-08-08):**
- `WITH CHECK` policies must NOT reference the target table's own columns inside a subquery — correlated subqueries see existing rows, not the NEW row (so they evaluate false/NULL on INSERT). Use SECURITY DEFINER helpers with the NEW value passed as an argument (e.g. `is_business_owner(business_id)`, `can_sell_batch(batch_id)`).
- `INSERT … RETURNING` (what PostgREST/`supabase_flutter .select()` uses) also applies the SELECT policy to the returned row. During onboarding the owner's SELECT policy returned NULL (`my_business_id()` unresolved), so `bp_select`/`bp_update` now also accept `is_business_owner(business_id)` and phone-claim (`user_id IS NULL AND phone = my_phone()`).
- Policy subqueries between mutually-referencing tables (business_partners ↔ user_profiles) must go through SECURITY DEFINER helpers to avoid infinite-recursion detection.
